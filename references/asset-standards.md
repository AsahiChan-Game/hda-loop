# 平台、用途与交付标准

资料核对：2026-09-08。来源与适用边界见 [standards-sources.md](standards-sources.md)。以下是基于公开官方指南整理的制作框架，不是统一行业认证，也不是各工作室未公开的内部规范。项目明确合同优先，具体引擎特性按安装版本核对。

## 先选三个维度

**平台/渲染路径 × 资产用途/观看条件 × 美术风格** 共同决定规格。手游可以写实，影视可以卡通；高面数、8K 贴图、PBR 或 Nanite 都不能单独代表高质量。

开始任务时形成简短资产规格，记录：

- 目标设备档位、引擎与渲染路径；实时游戏、实时过场或离线成片。
- 主角/近景、常用中景、背景或大量重复件；实体尺寸、最近视距、画面占比、同屏数量与镜头运动。
- 风格与辨识特征，使用 [art-direction.md](art-direction.md) 确定造型和表面要求。
- 几何/渲染顶点、材质槽、贴图驻留、透明/阴影、组件/实例、cook 和运行/渲染时间预算；每项标明项目规定、估算或实测。
- 第一阶段可在 Houdini 检查的条件、需要用户看图判断的条件、确认后才在 UE/目标设备检查的条件。

不自动为一个任务生产所有平台版本。多平台时选择实际需要的输出预设，保留共同设计和高质量源，各预设独立验证。

## 平台与渲染档位

| 档位 | 优先分配内容成本 | Houdini 中准备与检查 | 用户确认后验证 |
|---|---|---|---|
| 广覆盖手游 | 轮廓、必要材质信息、少量可读细节 | 低成本几何与 LOD、共享材质/图集候选、透明面积和小三角风险、简化碰撞数据 | 实际低端目标机的渲染支持、帧时间、内存、发热后持续表现；桌面预览不足以通过 |
| 高端手游 | 近景特征和有限高质量材质，按设备分档 | 保留可降级的几何/贴图/阴影方案，核心造型不能依赖最高档功能 | 实际设备/渲染路径的质量档切换、温度与功耗影响，不假定桌面效果全部可用 |
| 主流 PC/主机实时游戏 | 常用镜头下轮廓、材质与交互 | LOD 或项目支持的几何路线、实例化模块、碰撞与可动件边界 | 目标配置和代表场景密度的 CPU/GPU 帧时间、流送及碰撞；公开指南不代替主机专有认证要求 |
| 高端实时/AAA 近景 | 英雄物件细节、复杂材质与密集场景 | 高质量源及可用运行输出；按对象选择 Nanite/传统网格，保留必要 fallback | 几何、着色、遮罩、阴影、WPO、实例和流送的综合成本；Nanite 不保证整场景免预算 |
| UE 实时影视/过场 | 镜头构图、近景连续性和最终光照 | 满足镜头范围的细节和动画/表面稳定性 | 实际实时路径与播放帧率；使用 MRQ 离线采样的结果另作离线输出标注 |
| 离线影视成片 | 最终分辨率下轮廓、细分/置换、材质与时间连续性 | 按镜头需要准备细分源、UDIM/置换/曲线等，保留可解析依赖与渲染属性 | 指定渲染器中的噪声、采样/降噪、运动模糊、色彩、序列稳定性、内存和每帧时间 |

上述优先级是本工具建议。移动优化依据 [Google 几何/贴图指南](https://developer.android.com/games/optimize/geometry) 和 [Epic 移动渲染指南](https://dev.epicgames.com/documentation/en-us/unreal-engine/mobile-rendering-and-shading-modes-for-unreal-engine)；实时与离线路径区别见 [Epic Ray/Path Tracing](https://dev.epicgames.com/documentation/unreal-engine/ray-tracing-and-path-tracing-features-in-unreal-engine)。旧资料里的设备限制不直接当成新设备硬上限。

“影视级”首先明确指高品质实时资产还是离线镜头资产。本技能默认第二阶段仍为 UE 集成/验收；离线品质参考不自动改成其他渲染器交付，也不自动创建 USD、毛发或模拟管线。用户指定 UE Path Tracer/MRQ 时按离线渲染记录。纯 Houdini 离线成片属于明确变更的交付范围，不能伪造 UE 图或默默省略原约定。

## 类型与观看条件修正

| 对象或用途 | 必须额外考虑 |
|---|---|
| 第一人称武器、近距离道具 | 常见视角的轮廓/表面，活动零件、枢轴、隐藏接合面与动画间隙；不把场景小物的预算直接套用 |
| 俯视/MOBA/策略场景 | 缩小后的识别、方向、色块与地面区分；细节集中到真实可见区域，不照搬 Dota 的固定配色或上下渐变 |
| 开放世界建筑/城市 | 模块接缝、室内覆盖、通路、实例密度、分区/HLOD/流送；单栋成功不等于整城成功 |
| 植物/藤蔓 | alpha 覆盖、双面、叶簇体积、风权重、阴影和远处闪烁；面数低仍可能 overdraw 很高 |
| 角色/可变形资产 | 关节和表情拓扑、蒙皮、骨骼/LOD 一致性及变形测试；静态 HDA 体检不能替代角色验收 |
| 毛发、布料、液体或 VFX | 曲线/卡片/缓存等目标表示及专项时间连续性、碰撞和材质成本；没有对应能力时注明缺口，不套用静态网格通过标准 |

## 通用技术检查：选择适用项

1. **几何与尺度**：实际三角数、渲染顶点、包围盒、单位、轴向、pivot、装配锚点。检查退化、自相交和错误法线；叶片或设计为薄片的部件不强制封闭，静态中间网格不强制全四边形。骨骼/细分需求另定拓扑条件。
2. **细节分配**：让几何服务于轮廓、曲率和必要断面；平面不因密度高而更优。源模型与平台产物分开保留；已合格网格不重复减面。使用 `game-model-postprocess` 时按对象选择适用检查，具体 Nanite/影视路径由项目验证，不自动把高模一律判为不可用。
3. **UV 与贴图**：记录 texel density 的依据与允许差异、重叠用途、接缝、padding 和 mip 情况。可平铺、trim、图集或独占 UV 按用途选择；只有确实使用静态烘焙光照时要求相应 lightmap UV。UDIM 不是影视必选，也不能假定所有实时路径支持。
4. **法线与材质数据**：最终三角化/切线基与烘焙一致，明确法线约定；颜色贴图与 normal/roughness/metallic 等数据贴图区分色彩解释。通道打包按项目说明，不能认定所有 ORM 排列相同。压缩后重新检查，不把源 PNG 尺寸当驻留显存。
5. **成本结构**：除面数外记录材质槽/复杂度、阴影、透明覆盖、骨骼/WPO、实例/组件以及总驻留内容。共享材质是批处理的有利条件之一，不保证不同对象一定合成一次 draw call。
6. **运行表示**：按项目选择 LOD、Nanite、fallback、碰撞、实例和流送。Houdini 准备相应数据，实际输出设置及行为在用户确认后于 UE 检验。碰撞形体与可视模型的用途不同，不默认用完整渲染网格作动态碰撞。
7. **交付与维护**：源/产物分离、版本/哈希、HDA 依赖、三变体预设、资源路径及必要许可信息。大型影视资产可按项目用 [OpenUSD](https://openusd.org/release/intro.html) 管理引用和层级，但格式本身不证明材质兼容或视觉合格。

## 如何确定数值预算

不提供伪装成行业标准的“手游每件几千面、AAA 每件几十万面、影视必须 8K”。同一栋楼的俯视背景和近景可进入版本不能按同一个数字验收。[Google 的几何指南](https://developer.android.com/games/optimize/geometry) 也将设备、可见细节与使用条件纳入取舍。

先用项目已有合格资产/设备预算确定候选，再按代表场景校准。第一步记录估算，不为测预算提前进入 UE；用户确认后才做目标机测试。性能不合格时修复当前瓶颈；显著改变已批准造型则回到 Houdini 更新三图确认。

可计算的量作为解释工具，而非自动通过线：

- 帧预算 `1000 / FPS`：30、60、120 FPS 分别约 33.33、16.67、8.33 ms，属于整个帧，不属于单个资产；CPU/GPU 有重叠，不能简单把两者耗时相加当帧时间。
- 常规方形纹理完整 mip 链约为基础层的 4/3；分辨率边长翻倍，存储量约增四倍。以 **8 bit/像素的压缩纹理**、完整 mip 驻留且不计额外开销为例：1024² 约 1.33 MiB，2048² 约 5.33 MiB，4096² 约 21.33 MiB。它不是所有压缩格式的统一大小；VT、流送、ASTC block 大小和通道格式需另外核算。
- 纹理密度可以 px/m 记录，但数值来自镜头与实际清晰度，不把 512 或 1024 px/m 当统一标准。

## 两阶段如何使用这些要求

**第一步/Houdini**：选适用档位和艺术要求，检查结构、UV/属性、几何/贴图估算、HDA 鲁棒性及 A/B/C 的品质；展示三个真实变体并等待用户满意。阶段报告区分已测、估算和 UE 待验证。

**第二步/用户确认后的 UE**：实现必要材质/输出设置，用相同文件和预设复现 A/B/C，执行真实渲染/碰撞/性能检查，再交对应三张 UE 图。影视离线图标注渲染器/采样与帧时间；不能将离线高质量图充作实时性能证明。
